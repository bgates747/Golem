# 2026-07-28 — Project kickoff

## Summary

Started exploring whether the Agon Console8 VDP's **Buffered Commands API**
(`docs/vdp/Buffered-Commands-API.md` in the `agon-docs` repo) could serve as
a compilation target for a real programming language, rather than just a
macro/scripting facility for BASIC programs.

## Assessment of the Buffered Commands API

Concluded the API is a genuine stored-program machine and is (practically)
Turing-complete:

- **Memory**: buffers (up to 65,534), addressed by `bufferId` + up to a
  24-bit offset, or by block index. Buffers can hold multiple blocks and
  grow arbitrarily large.
- **Arithmetic/logic**: command 5 ("adjust buffer contents") provides NOT,
  negate, set, add, add-with-carry, AND, OR, XOR on buffer bytes, with
  "multiple target"/"multiple operand" modes and buffer-fetched operands.
- **Conditionals**: commands 6/8/10 support `==`, `!=`, `<`, `>`, `<=`,
  `>=`, `AND`, `OR`, and existence checks, against buffer bytes or VDP
  Variables (8-bit or 16-bit).
- **Control flow**: commands 1/7/9/11 provide call, jump, and jump-to-offset
  (with automatic tail-call optimization turning a trailing conditional
  call into a jump).
- **Self-modification**: command 5 can rewrite the bytes of a command
  sequence in place — this is explicitly intended (the docs describe using
  block offsets to make it easier to locate parameters to modify).

This is architecturally closer to an early stored-program computer (e.g.
EDSAC) than a modern CPU: no general-purpose registers, no hardware
multiply/divide/shift, and — critically — **no indexed/pointer-dereference
addressing mode**. Runtime-computed addresses (arrays, pointers,
stack-relative locals) can only be implemented via self-modifying
"patch the command, then execute it" code.

## Key gaps identified for a compiler backend

1. No integer multiply/divide/shift primitives — must synthesize via a
   runtime library (shift-add, restoring division), as is standard for
   8-bit MCU compilers without hardware multiply.
2. No indirect/indexed addressing — arrays, pointers, and stack frames need
   self-modifying code (patch offset/bufferId bytes before executing).
3. Comparisons are capped at 16 bits — wider comparisons need to be
   decomposed byte-by-byte.
4. Recursion is risky: the VDP's internal call stack can overflow and crash
   it. Tail calls are free (converted to jumps); non-tail recursion should
   be bounded or implemented as an explicit software stack.
5. No general floating point, except a possible (unverified) trick: command
   34's arbitrary-dimension matrix ops support add/sub/multiply/scalar-
   multiply/invert, and a 1x1 "matrix" is just a scalar — so `invert` on a
   1x1 matrix may yield a reciprocal, giving scalar add/sub/mul/div. Needs
   verification on real hardware before relying on it.

## Proposed compiler architecture

- Emit **one instruction per buffer block**, rather than hand-counting
  bytes into a single write-block command. This makes block index a clean
  program-counter/address unit and avoids the byte-counting pitfalls the
  API docs repeatedly warn about.
- A simple typed three-address-code IR, with explicit widening passes for
  multi-byte integers (add-with-carry chains) and explicit patch-then-
  execute pseudo-ops for array/pointer/local-variable access.
- Memory allocation: globals get fixed `bufferId`/offset at compile time;
  locals live in a shared stack buffer with frame-relative access compiled
  to self-modified offsets patched in the function prologue; heap
  objects/arrays get a buffer or buffer region, indexed via patch-then-
  execute.
- A hand-written runtime library (multiply, divide/mod, shifts, memcpy,
  string ops) resident in VDP buffers, called like any other function —
  avoiding the eZ80-VDP round trip that makes per-call chattiness
  expensive.
- Loader/linker: rather than streaming many small `write block` commands at
  load time, ship the compiled program as one compressed blob, decompress
  it into a scratch buffer (command 65), then use the split/spread commands
  (16-22) to fan it out into the program's statically assigned buffer IDs
  in a couple of VDU calls.

## Suggested language shape

A small C-/Pascal-like language: static/arena-allocated arrays,
struct-as-byte-layout, 8/16-bit integers as the fast path (32-bit taxed),
`while`/`for`/`if` compiled straight to jumps, tail-call-preferred function
calls, no/bounded recursion initially, no general floats initially (revisit
the 1x1-matrix trick once verified).

## Naming

Brainstormed project names (Agonal, Stadion, Palaestra, Dromos, Blockwright,
Bufferlang, Selfmod, Patchwork, Loom, Vdulang, Chimera, Frankenbuf, Golem).

Settled on **Golem** — buffers are inert "clay" until a sequence of
commands is inscribed into them, at which point they're animated into a
callable "function"; a fitting metaphor for a language built on
self-modifying, VDP-resident command buffers.
